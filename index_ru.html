Продвинутый prompting и Skills

Модуль 1 · Занятие 1 из 4

Обязательно
  • Пятиэлементная модель, файлы как часть контекста
  • Приёмы: пример в запросе, теги, итеративное уточнение, разбиение на шаги
  • Skills: формула Description, где находятся, проверка через Thinking
Желательно
  • «Правило двух месяцев» для качества skill
  • Три типичные ошибки при создании skill

Цель: Научиться формулировать чёткие запросы к Claude (пятиэлементная модель и пять приёмов) и оформлять повторяющиеся задачи в Skill, который Claude применяет автоматически.

Инструменты/понятия:

  • Типы текстовых задач: написание с нуля, редактирование и сокращение, смена тона, перевод, структурирование.
  • Промпт (разовый запрос) против Skill (инструкция для повторяющейся задачи).
  • Пятиэлементная модель промпта: Персонаж, Цель, Контекст, Формат, Ограничения.
  • Файлы как часть контекста (Word, Google Docs, PDF, Excel, CSV, изображения, презентации; добавляются через «+»).
  • Теги <текст>…</текст> и <завдання>…</завдання> для разделения материала и инструкции.
  • Skill: поля Skill name, Description, Instructions, Add file; способы создания Upload skill / Create a skill / Create with Claude; Settings → Customize → Skills (Browse, Add).
  • Формула Description: [что делает] + "Use when" [триггер]; три способа описать skill (инструкция для нового сотрудника из 4 вопросов; формула Format + Tone + Example; формула Description); «правило двух месяцев»; строка «Reading [название skill]» в Thinking.

Порядок работы:

  1. Определить тип текстовой задачи и решить, что подходит: промпт (разовая задача) или skill (повторяющаяся). Обратить внимание: если задача не повторяется, достаточно обычного промпта.
  2. Составить промпт по пятиэлементной модели (персонаж, цель, контекст, формат, ограничения). Обратить внимание: размытый запрос даёт размытый ответ; модель отвечает только на основе того, что написано.
  3. При необходимости прикрепить файл и чётко сказать, что с ним сделать. Обратить внимание: файл не заменяет чёткой постановки задачи; короткий запрос с файлом часто точнее длинного пересказа. Длинный текст, вставленный прямо в сообщение, разметить тегами.
  4. Применить приёмы: пример в запросе (1–2 одинаково оформленных образца); разбивка сложной задачи на шаги (сначала план, потом развитие пунктов); продолжение по образцу (написать начало самому); порядок «сначала весь материал, потом вопрос»; при неудачном ответе — перефразировать запрос.
  5. Для повторяющейся задачи описать skill (4 вопроса: когда применяется, какие шаги, какие правила, какой результат считается хорошим; либо Format + Tone + Example).
  6. Создать skill: Settings → Customize → Skills → Add → «Create with Claude» (Claude задаёт вопросы) или «Create a skill» (вручную). Обратить внимание: Skill name — латиницей через дефис (например, weekly-status-report), это идентификатор; Description — главное поле, по нему Claude решает, когда применять skill; Instructions — пошагово и конкретно; можно приложить образец через Add file.
  7. Проверить, что skill срабатывает: в новом чате сформулировать задачу своими словами, не называя skill, и найти в Thinking строку «Reading [название skill]». Обратить внимание: если строки нет, уточнить Description по формуле или назвать skill в запросе напрямую. Проверить «правилом двух месяцев»: понятно ли через два месяца, что skill делает.

Типичные ошибки, советы:

  • Skill слишком расплывчатый («пиши хорошие тексты» — пожелание, а не инструкция).
  • Skill слишком длинный: пытается предусмотреть все исключения и превращается в «роман».
  • Skill для одноразовой задачи.
  • Совет: уточнять результат отдельными короткими сообщениями, а не переписывать запрос заново.
  • Совет: если ответ не подходит, переформулировать запрос другими словами.

Итог в одну строку. Чёткий промпт (персонаж, цель, контекст, формат, ограничения) решает разовую задачу, а skill с точным Description («что делает» + "Use when") автоматизирует повторяющуюся.

Projects и углублённое создание skill

Модуль 1 · Занятие 2 из 4 · Связь: опирается на занятие 1 (skill)

Обязательно
  • База знаний проекта (Context) и инструкции проекта (Instructions)
  • Углублённый skill как полный рабочий процесс, а не только тон
Желательно
  • Scheduled tasks внутри проекта
  • Несколько skills в одном проекте одновременно

Цель: Научиться использовать Projects как рабочее пространство с общим контекстом для длительной темы и создавать skill, задающие целый рабочий процесс (структуру документа, шаги, образец результата).

Инструменты/понятия:

  • Project: блоки Instructions, Context, Scheduled, Memory (метка «Only you»); кнопки New project, «Use a folder», Create project; поля «What are you working on?» и «What are you trying to achieve?»; демонстрационный проект «How to use Claude».
  • Вызов skill командой через слеш (подсказка «Type / for skills»).
  • Description по формуле [что делает] + "Use when" [триггер]; рекомендации Anthropic: третье лицо («формирует отчёт», а не «я помогу»), конкретные ключевые слова-триггеры.
  • «Степень свободы» инструкции; объяснение причины вместо «всегда/никогда»; примеры (поле Add file, 3–5 образцов); статус Draft у созданного вручную skill.

Порядок работы:

  1. Решить, нужен ли проект. Обратить внимание: проект нужен, когда задача повторяется или длится долго, либо материалов по теме много; сигнал — «я уже в третий раз объясняю Claude одно и то же». Для разового запроса хватит обычного чата.
  2. Создать проект: Projects → New project → заполнить два поля → при желании «Use a folder» → Create project. Обратить внимание: один проект — одна чёткая тема (иначе «проект-свалка»).
  3. Заполнить Instructions («+»): тон, формат, постоянные требования. Обратить внимание: инструкция должна быть конкретной и проверяемой (пример: «обращайся на «Вы», избегай маркетинговых формулировок, даты в формате ДД.ММ.РРРР»); «пиши хорошо» не работает.
  4. Загрузить в Context документы и образцы; при необходимости настроить Scheduled (например, еженедельный отчёт по материалам проекта). Обратить внимание: Claude должен реально опираться на загруженное — проверять это запросом, ссылающимся на материалы.
  5. Спроектировать skill для рабочего процесса (структура документа, последовательность шагов, образец). Обратить внимание: примеры структур из материалов: протокол совещания (дата и участники; рассмотренные вопросы; решения; ответственные и сроки), коммерческое предложение (потребность клиента; решение; стоимость и сроки; следующие шаги), еженедельный отчёт (сделано; препятствия; планы), памятка клиенту/ученику (что сделать; в какие сроки; что будет, если не сделать; контакт).
  6. Выбрать уровень детализации. Обратить внимание: если ошибка дорого стоит или заметна (официальный документ, финансовый отчёт) — писать жёстко и подробно, по шаблону; для творческих задач оставлять Claude больше свободы.
  7. Писать причины, а не только приказы. Обратить внимание: «указывай дату, потому что без неё отчёт нельзя сопоставить с прошлыми выпусками» лучше, чем «всегда указывай дату».
  8. Приложить образцы (Add file); лучше 3–5 реальных образцов и попросить Claude сначала проанализировать общие паттерны, а потом сформировать skill.
  9. Разрабатывать skill вместе с Claude циклом: выполнить задачу обычным промптом и заметить, что приходится объяснять каждый раз → попросить Claude оформить подход как skill → проверить в новом чате без упоминания skill → вернуться с конкретным замечанием («забыл исключить тестовых клиентов») и доработать.
  10. Периодически обновлять проект (при смене формата, появлении нового правила, накоплении устаревших материалов; ревизия раз в месяц или квартал).

Типичные ошибки, советы:

  • Проект-свалка: в Context накапливаются слабо связанные темы «на всякий случай».
  • Устаревший Context (старая версия шаблона, которую не убрали).
  • Дублирование правил в Instructions проекта и в каждом skill (при изменении править в нескольких местах).
  • Проект вместо skill: если задача форматирования касается всех чатов, а не одного проекта, нужен skill.
  • Слабое Description вроде «помогает с документами» Claude не отличит от десятков других skills.
  • Совет: проект — живой инструмент, а не разовая настройка.

Итог в одну строку. Project хранит общий контекст и правила одной темы, а хорошо описанный skill с примерами фиксирует формат документа; создавать skill лучше циклом «попробовать, проверить на свежем примере, уточнить».

Модуль 1 · Занятие 3 из 4

  • Библиотека артефактов

Инструменты/понятия:

  • Агент: сам планирует шаги, выполняет их, проверяет промежуточные результаты, корректирует план и возвращается к пользователю по окончании или когда нужно решение.

Порядок работы:

  1. Выбрать подходящую задачу. Обратить внимание: Cowork лучше для рутинных многошаговых задач с понятным конечным результатом; для исследовательских и творческих задач, где вы сами уточняете цель в диалоге, естественнее обычный чат.

Обратить внимание: чем конкретнее критерий готовности, тем меньше ручных правок. Слабо: «напиши что-то о нашем новом продукте».   5. Проверять промежуточные результаты для важных задач. Обратить внимание: особенно когда задача объёмная и ранняя ошибка повлияет на всё, материал чувствительный или публичный, нет опыта; с доверием можно чаще ждать только финал.

  7. Определить уровень контроля: ориентир — риск ошибки, умноженный на стоимость её исправления. Обратить внимание: стилистическая правка в черновике — проверять реже; неверные цифры в финансовом отчёте или некорректная публичная информация — проверять внимательно; уменьшать частоту проверок осознанно, а не по умолчанию.

Типичные ошибки, советы:

  • Слишком расплывчатая цель («сделай текст лучше»): нет критерия завершения.
  • Нет источников: просьба «на основе наших материалов» без вложений заставляет Cowork выдумывать содержание.
  • Отсутствие промежуточного контроля для важных задач.
  • Противоположная крайность: слишком частые мелкие вмешательства сводят на нет выгоду делегирования.
  • Совет: ваша роль смещается с «дирижёра каждого такта» на того, кто ставит задачу и принимает результат.

Итог в одну строку. Cowork берёт на себя промежуточные шаги, если поставить ему конкретную цель с источниками, ограничениями и критерием «готово», а уровень проверки выбирать по цене возможной ошибки.

  • Совет: просить промежуточные шаги расчёта, а не только итоговое число.

Порядок работы:

  1. Установить надстройку: Excel → раздел надстроек → найти Claude for Excel → установить → войти в аккаунт Claude. Обратить внимание: доступность на платных планах.

  3. Найти и исправить ошибку: спросить причину и способ исправления. Обратить внимание: Claude должен проследить зависимости до первопричины (например, пустая ячейка в расчёте среднего) и предложить конкретное исправление (внести значение или добавить проверку перед делением).
  4. Обновить данные без потери формул. Обратить внимание: формулы должны пересчитаться, а не заменяться статическими числами; после обновления попросить перечислить изменившиеся ячейки и формулы. Различать «заменить формулу числом» и «изменить входной параметр», от которого формула посчитает нужное.
  5. Заполнить шаблон новыми данными, сохраняя структуру, форматирование и формулы; для модели с нуля сначала описать словами структуру (разделы, входные параметры, формулы), потом просить реализацию. Обратить внимание: формулы в колонках с суммами остаются формулами.
  6. Провести аудит файла перед важным решением: перечислить ячейки с ошибками или предупреждениями; найти формулы, случайно замененные числом; проверить, что итоги охватывают весь нужный диапазон. Обратить внимание: просить «ничего не менять», только перечислить проблемы с указанием листа, ячейки, причины и способа исправления.
  7. При необходимости сравнить две версии файла (до и после правок коллеги, этот и прошлый год) и настроить условное форматирование словами («подсвети красным месяцы, где расходы превысили бюджет более чем на 10%»), а также защиту листа (редактируются только ячейки входных данных). Обратить внимание: после массовых изменений проверять итоговые показатели.
  8. Помнить о границах применения. Обратить внимание: для одноразового простого подсчёта проще калькулятор; надстройка ценна для повторяющихся, сложных расчётов с многими параметрами и там, где важна прозрачность логики. Перед подключением финансовых файлов с чувствительными данными (зарплаты, маржа, персональные данные) проверить политику организации.

Типичные ошибки, советы:

  • Размытая ссылка на ячейку («это число неверное» без листа и адреса).
  • Игнорирование нескольких похожих листов (месяцы, отделы).
  • Нет проверки после массового обновления.
  • Путаница значения и формулы («сделай это число 500» может заменить формулу числом или изменить входной параметр).
  • Совет: перед каждым важным решением делать аудит; защищать ячейки с ключевыми формулами от случайных правок.
  • Совет: не подключать файлы с чувствительными данными без проверки политики организации.

Итог в одну строку. Claude for Excel работает прямо в открытой книге, видит формулы и связи между листами, поэтому годится для аудита, поиска ошибок и безопасного обновления данных, если указывать конкретные ячейки и проверять результат.

Projects + Skills для аналитики

Модуль 2 · Занятие 3 из 4

Обязательно
  • Проект под регулярную отчётность с базой знаний
  • Skill, фиксирующий стандартную структуру отчёта
Желательно
  • Несколько skills в одном проекте
  • Обновление базы знаний новыми данными

Цель: Научиться превращать регулярную аналитическую отчётность (ежемесячный отчёт о посещаемости музея) в связку «проект + skill», чтобы структура и стиль отчёта были одинаковыми от выпуска к выпуску, а меняются только цифры.

Инструменты/понятия:

  • Projects: Context (примеры прошлых отчётов, справочные данные, глоссарий) и Instructions (язык, тон, округление, правила комментариев).
  • Skill (SKILL.md): name, Description по формуле «[что делает] + Use when [триггер]», структура отчёта, правила сравнения, правила для исключений.
  • Разовый анализ и регулярная отчётность: для первого жёсткий формат только мешает.
  • Несколько skills в одном проекте: Claude сам выбирает подходящий по Description.
  • Дашборд, файлы Excel с формулами, презентация, прогноз по формуле.

Порядок работы:

  1. Создать проект под регулярную отчётность и загрузить в Context пример прошлого отчёта, справку с планами и таблицу данных. Обратить внимание: в Context только 1–2 образцовых отчёта и актуальные справочные данные, без «исторического мусора на всякий случай». Образцы отчётов служат только образцом стиля, цифры берутся из таблицы.
  2. Прописать Instructions проекта: язык (украинский), стиль, округление (посетители — целые, проценты — до 1 знака), откуда брать планы, термины по глоссарию, правило «отклонение от плана более 15% — объяснить причину одним предложением», запрет выдумывать данные. Обратить внимание: такие мелочи отличают отчёт, который выглядит одинаково профессионально из месяца в месяц.
  3. Запустить первый отчёт без skill и проверить источник цифр (попросить показать строки таблицы и сумму). Обратить внимание: совпадает ли сумма строк с итогом в отчёте; похож ли отчёт на образец. Для сентября: 569 + 259 + 285 + 127 = 1240 посетителей при плане 1260 (98,4%).
  4. Создать skill для стандартной структуры отчёта: краткий итог (3–4 предложения), ключевые показатели (таблица), график (1–2), детализация по типам посещения, выводы и рекомендации (2–3 пункта), объём до двух страниц. Обратить внимание: пять разделов в нужном порядке; skill не должен быть слишком жёстким (лучше «2–4 графика в зависимости от данных», чем «ровно 5»).
  5. Проверить skill на разных объёмах данных, в том числе на файле без предыдущих месяцев. Обратить внимание: честно ли Claude пишет, что данных для графика динамики нет, а не выдумывает их.
  6. Добавить правило сравнения: текущий месяц с планом, с прошлым месяцем и с тем же месяцем прошлого года, с разницей в людях и процентах; если данных нет, так и написать. Обратить внимание: без базы сравнения голые цифры малоценны; проверить порядок строк и совпадение цифр между таблицами отчёта.
  7. Собрать дашборд (главные цифры, линейный график по месяцам за 2025 и 2026, столбчатый «факт и план», таблица отклонений), вносить правки отдельными сообщениями (цвета, подсветка строк с отклонением более 15%, фильтр по типу). Обратить внимание: плана на месяцы, которых нет в справке, быть не должно (справка содержит планы только на июль–октябрь 2026, на январь–июнь планов нет); должно быть видно, откуда взялись числа.
  8. Создать второй skill — краткую справку для директора (до полстраницы, без таблиц и графиков: три главные цифры одним абзацем, одно предложение о наибольшем отклонении, 2–3 рекомендации). Обратить внимание: выбрал ли Claude именно короткий skill; сходятся ли цифры с полным отчётом. Разные аудитории требуют разных skills.
  9. Обработать новые данные за октябрь: сначала проверить, не загружая в проект (сравнить со средним за июль–сентябрь и октябрём 2025, пометить подозрительные значения). Дописать в skill правила исключений: нет данных — прямо указать и не считать нулём; отклонение от плана более 50% — пометить «требует проверки» и не делать выводов. Обратить внимание: не все странные значения ошибки, часть можно объяснить сезонностью; сравнить отчёты до и после новых правил. В файле октября намеренно заложены две проблемы (студент должен найти их сам): «Оглядові екскурсії» = 2950 (план 270; октябрь 2025 — 270; июль–сентябрь 2026 — 223, 218, 259, в среднем около 233; отклонение от плана примерно +993%, то есть выше порога 50%) и пустая ячейка у «Онлайн-лекції» (план 120; в октябре 2025 — 99): её нельзя считать нулём. Остальные два значения (548 и 312) правдоподобны при плане 560 и 340.
  10. Исправить данные в самой таблице: администратор подтвердил 295 оглядовых экскурсий и 131 участника онлайн-лекций. Claude показывает «было и стало», затем дописывает исправленный октябрь в основную таблицу (новый файл «…с жовтнем.csv»); в проекте старую таблицу заменить новой. Обратить внимание: изменены ровно две ячейки; в проекте только одна таблица данных; в отчёте и на дашборде октябрь полный; в проекте два образца отчёта (август и октябрь). После правки октябрь = 548 / 295 / 312 / 131, всего 1286 при плане 1290 (99,7%); файл «…з жовтнем.csv» (88 строк данных) совпадает с таблицей до октября (84 строки), к которой добавлены 4 строки октября. Правка в таблице лучше, чем просьба «учесть правку в отчёте»: исправление тогда попадает во все будущие отчёты и дашборд.
  11. Производные файлы: Excel «Відвідування по кварталах» (суммы и проценты формулами), Excel-прогноз на ноябрь–декабрь, Excel для бухгалтерии в другой раскладке (месяцы в строках, типы в колонках, «Разом»), Excel-сверка отчёта с таблицей. Обратить внимание: клики по ячейкам должны показывать формулы, а не числа; общая сумма одинакова в обеих раскладках; при смене коэффициента прогноз пересчитывается; в сверке все строки «Збігається», а если нет, выяснить, ошибка в отчёте или в расчёте.
  12. Прогноз: значение того же месяца 2025 года умножить на коэффициент «октябрь 2026 / октябрь 2025»; показать коэффициент, расчёт по месяцам и список допущений; повторить по каждому типу посещения и сравнить итоги. Обратить внимание: допущения явные (например, сезонность такая же, как в прошлом году); на дашборде прогноз пунктиром и с подписью «прогноз», чтобы не спутать с фактом.
  13. Презентация для директора на 6 слайдов (титул, три цифры октября, график по месяцам, факт и план, прогноз с допущениями, три рекомендации), не более 4 коротких строк на слайд; слайд с прогнозом визуально отличается. Обратить внимание: цифры совпадают с отчётом и прогнозом; прогноз помечен.

Типичные ошибки, советы:

  • Слишком жёсткая структура skill (например, ровно 5 графиков) заставляет выдумывать лишнее или обрезать важное.
  • Нет правила сравнения: отчёт с голыми цифрами малоценен.
  • Игнорирование аудитории: для руководства и для аналитиков нужны разные skills.
  • Не перегружать Context лишней историей; образцы отчётов использовать только как стиль.
  • Skill редко идеален с первого раза: записывать, что приходилось править руками, и периодически вносить накопленные правки в сам skill. Полезно документировать, почему формат выбран именно так.
  • Явные правила для исключений (нет данных, аномалия), иначе Claude решает каждый раз по-разному.
  • Непроверенные данные не загружать в проект, а давать в чат.
  • Если пока нет ни одного образца отчёта, начать со словесного описания структуры; первый реальный выпуск станет образцом.
  • Всегда проверять источник цифр и сверять отчёт независимым расчётом.

Итог в одну строку. Регулярный отчёт = проект с Instructions и образцами + skill со структурой и правилами сравнения и исключений, а цифры всегда проверяются по таблице.

Cowork для комплексных аналитических задач + итоговый кейс

Модуль 2 · Занятие 4 из 4 · Связь: опирается на проект и skill занятия 7

Обязательно
  • Делегирование многоэтапной аналитики: несколько источников → сводный отчёт
Желательно
  • Scheduled tasks: автоматический отчёт по расписанию

Цель: Научиться делегировать Cowork многоэтапную аналитику по нескольким источникам (сводный квартальный отчёт) и при этом контролировать результат: проверять структуру источников, промежуточные шаги и неполные данные.

Инструменты/понятия:

  • Cowork (задача с подключённой папкой, внутри проекта и вне проекта).
  • Проект со skill «monthly-attendance-report» (из занятия 7).
  • Scheduled task (запланированная задача) для еженедельного итога.
  • Промежуточная проверка, обработка частичных источников, различие «подтверждено данными / предположение».

Порядок работы:

  1. Поставить Cowork конечную цель, а не диктовать шаги: результат, источники, стандарт подачи. Запускать задачу внутри проекта, чтобы подхватились skill, Context и Instructions. Обратить внимание: источников лучше 2–3 чётко структурированных; при 10+ источников разбивать на этапы через промежуточные файлы.
  2. Сводный отчёт за III квартал 2026: свести три таблицы отделов, сравнить с III кварталом 2025 только по таблице 2025–2026, план квартала как сумма месячных планов, выделить тип с наибольшим отклонением, сохранить Word в новую папку «Звіти» с названием «Звіт III квартал 2026». Обратить внимание: применились ли skill и правила проекта (пять разделов в порядке, проценты с одним знаком, пояснения отклонений более 15%); подтверждает ли каждый вывод цифры отчёта.
  3. Проверка структуры источников: онлайн-лекции прислали таблицу с другими названиями колонок (файл «Онлайн-лекції III квартал 2026 (інші колонки).csv» в папке «Варіанти для завдань»); Cowork создаёт подпапку «Архів», переносит туда старую таблицу, новую копирует в «Квартальний звіт» (ничего не удаляется). Запустить тот же запрос на отчёт (изменено только название файла отчёта); если Cowork не упомянул разницу колонок, отправить ещё одну задачу с явным требованием сначала сверить колонки и объяснить сопоставление. Обратить внимание: сообщил ли Cowork о расхождении (в ответе и в отчёте); чем отличаются ответы без явного требования и с ним. В конце вернуть файлы как было. Опасность: молчаливое самостоятельное сопоставление колонок может исказить данные незаметно.
  4. Промежуточная проверка: попросить свести данные в Excel «Зведена таблиця» и не писать отчёт до подтверждения; потребовать показать, из какого файла и каких недель взято каждое число и как будут считаться план и отклонение; сверить итоги июля–сентября с таблицей 2025–2026; только затем попросить отчёт «після перевірки». Обратить внимание: те же ли цифры в отчёте и в промежуточной таблице, прослеживается ли логика.
  5. Запланированная задача: каждый понедельник в 9:00 готовить краткий недельный итог по таблицам отделов (по типам и всего, к прошлой неделе) в «Звіти/Тижневі підсумки» с датой в имени файла; если по какому-то отделу нет данных за прошлую неделю, не считать сумму, а написать, чьих данных не хватает; ничего не выдумывать. Создаётся запросом в Cowork или кнопкой «+» в разделе «Заплановано» на странице проекта. Обратить внимание: появилась ли папка «Тижневі підсумки», соответствует ли итог реальным данным; если есть кнопка немедленного запуска, использовать её. Задача на компьютере работает, только пока он включён и в интернете.
  6. Поиск отклонений: найти тип с наибольшим отклонением от плана и объяснить причину, отдельно пометив «подтверждено данными» и «предположение»; сохранить в «Пояснення відхилення III квартал 2026». Обратить внимание: опирается ли «подтверждённое» на конкретные цифры, не выдано ли предположение за факт. Если выдано, дописать в SKILL.md: «Пояснення причин завжди позначай як підтверджені даними або як припущення.»
  7. Сравнение «внутри проекта и вне»: тот же отчёт сделать на главной странице с Cowork, выбрав только папку «Заняття 8», и сравнить со стандартом проекта. Обратить внимание: чем отличается результат без skill и Instructions (в практике .docx дан только запрос с названием отчёта «…поза проєктом», критерии и результат сравнения не описаны).
  8. Неполные данные: касса прислала файл без последней недели; сначала обычный запрос без инструкций, затем запрос, где сказано проверить наличие всех недель и при нехватке сделать предварительный отчёт с пометкой в начале и без сравнения неполных показателей с планом. Обратить внимание: заметил ли Cowork нехватку; видно ли с первого взгляда, что отчёт неполный. В конце вернуть файлы как было.

Типичные ошибки, советы:

  • Нет проверки источников: отчёт на неполных или неактуальных данных.
  • Слишком поздняя проверка: контролировать хотя бы один промежуточный этап.
  • Игнорирование различий в структуре источников (разные названия колонок): предупреждать об этом в задаче или требовать проверку.
  • Расписание без обработки исключений: молча выдаст некачественный результат; нужно прописать, что делать при неполных данных.
  • При частичных источниках выбрать заранее: ждать все или делать предварительную версию с пометкой (для жёстких дедлайнов обычно второе).
  • Доверие к автоматике растёт постепенно: сначала сверять цифры вручную, затем выборочно (например, полный аудит раз в квартал).
  • Окончательное решение, готов ли результат, всегда за человеком; роль человека смещается к интерпретации и улучшению процесса.
  • Полезно один раз сравнить время ручного сведения и делегированного запуска с проверкой.

Техническое задание и введение в Claude Design

Модуль 3 · Занятие 1 из 4

Обязательно
  • Spec-Driven Development, составление ТЗ через интервью с Claude
  • Что такое Claude Design и что можно создавать
Желательно
  • «Протекание» контекста в ТЗ
  • Статичный вариант против интерактивного

Цель: Освоить Spec-Driven Development: сначала составить ТЗ (с помощью интервью Claude), а затем впервые поработать в Claude Design и получить по ТЗ прототип страницы сайта Software and Computer Museum.

Инструменты/понятия:

  • Spec-Driven Development: полнота ТЗ важнее реализации; ошибка в ТЗ дороже ошибки в результате.
  • ТЗ и промпт: ТЗ как «маршрут», промпты как «остановки».
  • Структура ТЗ: цель и главное действие, аудитория, структура, тон и стиль, технические требования, открытые вопросы (в практике добавлены «Складність результату», «Візуальні орієнтири», «Наявні матеріали», «Побажання до стилю»).
  • «Утечка» контекста (посторонние данные из прошлых разговоров).
  • Статический и интерактивный вариант.
  • Claude Design (с сентября 2026 часть самого Claude): Slides, Design, Design System, Design in codebase, Motion (бета); живой канвас, артборды, комментарии, ручная правка, экспорт в PDF/PowerPoint/HTML, артефакты.

Порядок работы:

  1. Начать новый чат вне проекта (чтобы не было утечки контекста) и попросить Claude интервьюировать по одному вопросу. Обратить внимание: отвечать коротко и конкретно («родители с детьми, учителя, подростки», не «для всех»); если ответа нет — «запиши в открытые вопросы»; про цвета и шрифты давать только общее настроение («тёплый, музейный, слегка ретро»); сообщить про логотип и фирменные цвета, если они есть.
  2. Свести ответы в документ ТЗ с нужными разделами. Обратить внимание: структура соответствует чек-листу.
  3. Вычистить «утечку» контекста: попросить Claude пометить пункты, не следующие из ответов, и откуда они могли взяться; проверить самому (особенно слишком уверенные цифры, названия, требования); переписать ТЗ начисто, сравнить версии. Обратить внимание: не исчезло ли нужное.
  4. Решить сложность результата: таблица «блок, статичный или интерактивный, почему»; зафиксировать пункт «Складність результату», что можно добавить позже, вынести в открытые вопросы. Обратить внимание: для учебных и презентационных задач чаще достаточно статического варианта.
  5. Проверить главное действие посетителя: найти предложение, которое прямо его называет; если нет, дописать в начало раздела «Мета й головна дія». Обратить внимание: без главного действия дизайну «некуда вести».
  6. Проверить ТЗ по чек-листу (таблица: какие разделы есть, каких нет, какие неполны), дописать недостающее (при нехватке информации Claude сначала задаёт вопрос), вынести нерешённое в «Відкриті питання».
  7. Подготовить ТЗ к дизайн-системе: добавить «Візуальні орієнтири» (2–3 сайта музеев и что именно нравится, словами, так как Claude не всегда открывает ссылки), «Наявні матеріали» (логотип, фирменные цвета, фото), «Побажання до стилю» (словами, без конкретных цветов и шрифтов); оформить Word «ТЗ — Сайт музею» и сохранить. Обратить внимание: в ТЗ не появились цвета и шрифты, которых вы не называли; для каждого примера записано, что нравится.
  8. Первое знакомство с Claude Design: раздел «Дизайн», карточка «Дизайн», загрузить ТЗ (выбор дизайн-системы пропустить), попросить простой прототип с реальными текстами и отметками там, где данных не хватает (не выдумывать). Слева чат, справа канвас, обычно два артборда (компьютер и телефон). Оставить один комментарий с правкой к элементу. Недостающее по словам Claude добавить в «Відкриті питання» и обновить ТЗ. Обратить внимание: цвета и шрифты прототипа произвольны, настоящий стиль задаст дизайн-система на занятии 10.
  9. Функционал: попросить три принципиально разных варианта первого экрана рядом и оставить лучший; проверка удобства и читабельности (шрифт, иерархия, телефон) с исправлением трёх главных проблем; одна ручная правка на канвасе; экспорт в PDF. Обратить внимание: варианты отличаются по сути, а не цветом; проблемы реально исправлены; PDF открывается. Для сайта экспорт не нужен.

Типичные ошибки, советы:

  • Слишком общая формулировка («сделай красивую страницу»).
  • Нет главного действия посетителя.
  • Посторонние данные в ТЗ из-за утечки контекста; безопаснее начинать новый чат под ТЗ.
  • Чрезмерная детализация на старте: сначала структура, детали на этапе макета.
  • Если решение принимает не один человек, показать ТЗ другим до визуализации (текст править дешевле макета).
  • Для простой разовой картинки хватает короткого описания; полное ТЗ нужно, когда есть несколько связанных частей, несколько участников или дорогая ошибка.
  • Фиксировать открытые вопросы честно, а не изображать полную определённость.
  • ТЗ сохранить отдельным файлом: оно нужно на занятиях 10–12 и при создании сайта.

Дизайн-система и макеты

Модуль 3 · Занятие 2 из 4 · Связь: опирается на ТЗ из занятия 9

Обязательно
  • Дизайн-система: цвета, шрифты, отступы, состояния кнопок
  • Логика главной страницы: hero, призыв к действию, футер
Желательно
  • Плейсхолдеры для контента
  • «Какое действие хотим от посетителя» важнее цвета

Цель: Создать дизайн-систему сайта музея по ТЗ и собрать из неё макеты главной страницы для компьютера и телефона, обращая внимание на главное действие и доступность.

Инструменты/понятия:

  • Дизайн-система (отдельный тип «Design System» в Claude Design): цвета (3–5), шрифты и размеры, отступы, элементы и их состояния (обычное, при наведении, нажатое). Хранится в настройках и подтягивается в новые дизайны; Claude сверяет результат с системой.
  • Можно создать с нуля по ТЗ или на основе имеющихся материалов (логотип, брендбук, код на GitHub).
  • Структура страницы: hero, call to action (CTA), основной контент, футер.
  • Иерархия внимания, плейсхолдеры, WCAG AA, mobile-версия, артборды.
  • Синхронизация Claude Design и Claude Code (модуль 4).

Порядок работы:

  1. Создать дизайн-систему из ТЗ, перенеся в запрос ключевое: тон, аудитория, платформа, главное действие, стиль, фирменные цвета, шрифты с полной кириллицей, основной текст не менее 18 px, отступы, три состояния кнопки; приложить ТЗ и файлы логотипа/обложки. Затем попросить объяснить выбор и проверить контраст по WCAG AA, дать системе понятное название («Сайт музею»). Обратить внимание: не более пяти цветов; шрифты поддерживают украинский; у кнопки три состояния; Claude называет конкретные значения контраста и связывает выбор с ТЗ.
  2. При неуверенности запросить два принципиально разных варианта (светлый как на обложке музея и тёмный неоновый ретро 80–90-х) и сравнить рядом. Обратить внимание: читабельность неонового варианта (к вопросу вернутся на занятии 11).
  3. Собрать страницу: применить систему к прототипу занятия 9 (если нельзя подключить, создать новый дизайн), блоки в порядке из ТЗ, заменить отметки «[ЗАПОВНИТИ]» реальным содержимым (тексты из ТЗ, шесть фото экспонатов, телефон, адрес, рабочий переключатель UA / EN). Обратить внимание: применены цвета и шрифты системы; Claude не выдумал цен, экскурсий, экспонатов; английский текст вмещается в кнопки и карточки.
  4. Переделать hero: сохранить старый вариант артбордом «Hero до правок», оставить заголовок и два входа («Курси» и «Екскурсія», карточка курсов чуть заметнее), заменить абстрактную графику фото зала с синим затемнением, сравнить варианты. Обратить внимание: за секунды понятно, что это за страница и что делать; лишние кнопки отвлекают от главного действия.
  5. Вариант для телефона: блоки друг под другом, входы видны без прокрутки, круглая кнопка звонка закреплена справа; проверить на реальном телефоне в разделе «Артефакти». Обратить внимание: не потерялись блоки, текст не мал, кнопки не стоят слишком близко.
  6. Иерархия внимания: уменьшить масштаб или прищуриться, определить, что заметнее всего; если не главная кнопка, попросить усилить размер и контраст нужного элемента и приглушить второстепенные, не меняя цвета системы.
  7. Проверка доступности: таблица контраста WCAG AA; исправления вносить в саму дизайн-систему, а не только в макет; основной текст не менее 18 px для взрослой аудитории. Обратить внимание: макет обновился вместе с системой.
  8. Подготовить макет к сайту: попросить список недостающих страниц и блоков (первая версия или позже), добавить в «Відкриті питання» ТЗ, выпустить новую версию Word. Обратить внимание: в разделе «Дизайн» сохранены и дизайн-система, и макет (их передадут в Claude Code).

Типичные ошибки, советы:

  • Слишком много цветов (более 5 основных).
  • Макет без системы: при нескольких материалах получается рассогласование.
  • Нет явного призыва к действию.
  • Игнорирование малого экрана.
  • Игнорирование доступности: просить её прямо в запросе, а не надеяться.
  • Принцип «действие важнее цвета»: самый заметный элемент должен соответствовать главной цели; один явный главный элемент на экране.
  • Править короткими итеративными правками; после 3–4 правок смотреть свежим взглядом.
  • Не ждать идеальных фото: плейсхолдеры допустимы, но перед сайтом заменить реальными текстами и фото хотя бы на главной.
  • Для одного разового результата полная система может быть избыточна.
  • Тестовый приём: показать макет коллеге без объяснений и спросить, что должен сделать посетитель.
  • Перед генерацией системы напомнить Claude ключевые пункты ТЗ (тон, аудитория, цель).
  • Экспорт в картинку/PDF для сайта не нужен: Claude Code работает с самим дизайном.

Шрифты, доступность и читабельность

Модуль 3 · Занятие 3 из 4 · Связь: работает с дизайн-системой занятия 10

Обязательно
  • Accessibility: контраст, размер, подписи
  • Проблема кириллицы в декоративных шрифтах
Желательно
  • Эффекты не должны вредить читабельности
  • Проверка на реальном экране

Цель: Довести макет до удобного для всех состояния: проверить доступность по WCAG AA, шрифты и кириллицу, подписи, размеры, эффекты, и вносить исправления в дизайн-систему.

Инструменты/понятия:

  • Доступность (accessibility), стандарт WCAG (уровень AA).
  • Контраст: обычный текст минимум 4,5:1, крупный (от ~24 px, жирный от 19 px) минимум 3:1.
  • Размер и расположение текста: основной не менее 16 px (для 40+ лучше 18), межстрочный около 1,5, строка до ~80 знаков, выравнивание по левому краю.
  • Понятные подписи кнопок и ссылок, alt-текст изображений, иконки с подписью, смысл не только цветом.
  • Размер целей нажатия (ориентир Apple: не менее 44 pt).
  • Шрифты и кириллица: панграмма, апостроф, «ҐЄІЇ»; Google Fonts (фильтр Language), itch.io; лицензия.
  • Эффекты и читабельность; проверка на реальном экране.

Порядок работы:

  1. Узнать, какие шрифты в системе, и создать артборд «Зразок шрифту» с панграммой «Чуєш їх, доцю, га? Кумедна ж ти, прощайся без ґольфів!», словами «пам'ять» и «м'ята», «ҐЄІЇ», цифрами и знаками, размерами 48/32/18/16 px, заголовком, абзацем и кнопкой. Обратить внимание: на месте ли ґ, є, і, ї и той же ли они толщины; не заменился ли апостроф и нет ли странного отступа; одинаковой ли высоты заглавные; цифры не из другого ли шрифта. Метка «Cyrillic» не гарантирует полный украинский набор. Декоративный (особенно пиксельный) шрифт часто проваливает проверку.
  2. Подобрать 2–3 простых шрифта на Google Fonts с фильтром украинского языка и тестовой панграммой, сделать такие же образцы на артбордах, сравнить на компьютере и телефоне (особенно 16–18 px), выбрать шрифт основного текста, обновить дизайн-систему (декоративный оставить только для крупных заголовков), убрать образцы с канваса. Обратить внимание: лицензия шрифтов (у шрифтов с itch.io разные); файл шрифта можно загрузить в раздел Typography дизайн-системы.
  3. Проверить контраст всех пар в системе, включая кнопки во всех состояниях, карточки и футер; исправить в системе (затемнять или осветлять, а не менять стиль полностью); убедиться, что макет обновился.
  4. Подписи и кнопки: найти неописательные («Детальніше», «Тут», «Перейти») и иконки без подписи, переписать (пример «Про сімейну екскурсію»), добавить alt-тексты (список «изображение — alt»). Обратить внимание: нет «Детальніше» без пояснения; у каждого изображения есть описание; ошибки в форме обозначены не только красным, но и текстом.
  5. Эффекты: таблица «элемент, эффект, мешает ли чтению»; сохранить версию «До правки ефектів», убрать или ослабить главный мешающий эффект, сравнить рядом. Обратить внимание: эффект уместен, если без него текст читается так же хорошо; подложка или затемнение под текстом на фото обычно сразу улучшают чтение, свечение можно оставить на одном крупном заголовке.
  6. Полная проверка доступности (десктоп и телефон): контраст, размер текста, интервал, длина строки, подписи, alt, размер и расстояние кнопок; таблица «элемент, проблема, как исправить, где исправлять» (в системе или в макете). Исправить, повторить проверку, сравнить до и после, убрать вспомогательные артборды, оставить финальные варианты для компьютера и телефона. Обратить внимание: в обновлённой таблице проблем нет; обновлена дизайн-система, а не только макет; телефонный вариант тоже проверен.
  7. Проверка на реальном экране: открыть дизайн в приложении Claude на телефоне (раздел «Артефакти»), читать на вытянутой руке, при ярком свете, в очках и без; лучше попросить человека из аудитории прочитать вслух (запинки указывают на проблемы).

Типичные ошибки, советы:

  • Выбор шрифта по названию или красивому образцу без проверки на украинском тексте (проверять на реальном тексте, а не на одном слове).
  • Светло-серый текст «для стиля», не проходящий контраст.
  • Декоративный шрифт для всего текста вместо одних заголовков (обычно достаточно двух шрифтов).
  • Проверка только на компьютере.
  • Правки в отдельном макете вместо дизайн-системы (не распространяются на другие страницы и код).
  • Тени, обводки и градиенты на основном тексте, заглавные буквы в длинных абзацах, тонкий светлый шрифт, мигание и движение текста.
  • Проверка Claude полезна, но не заменяет реальных людей; сочетать оба способа.
  • Лицензия шрифта: шрифты Google Fonts обычно с открытой лицензией, для остальных сначала проверять условия.
  • Фильтр по кириллице на Google Fonts не даёт полной гарантии.

Итог в одну строку. Проверить шрифты на украинском тексте, контраст и подписи, убрать вредные эффекты и все исправления вносить в дизайн-систему.

Практический кейс: комплексный дизайн-проект

Модуль 3 · Занятие 4 из 4 · Связь: объединяет занятия 9–11

Обязательно
  • Полный цикл: ТЗ → дизайн-система → макет → проверка доступности
  • Итоговый кейс
Желательно
  • Экспорт (PDF, PPTX) или передача в Claude Code

Цель: Пройти на одном примере весь путь модуля (ТЗ, дизайн-система, макет, проверка шрифтов и доступности, обратная связь, передача дальше) и получить проверенный прототип, который станет отправной точкой для модуля 4 (рабочий сайт). Сквозной пример: страница нового курса музея; вместо неё можно взять страницу мероприятия, вакансии, услуги или продукта, если она нужна вам как сайт.

Инструменты/понятия:

  • Полный цикл: ТЗ (занятие 9), дизайн-система и макет (10), проверка (11), передача (12 и модуль 4). У каждого этапа свой результат, который проверяют, прежде чем идти дальше: чем раньше найдена ошибка, тем дешевле её исправить.
  • Claude Design: раздел «Дизайн», «Design System», проект «Design»; артефакты сначала приватные, обратная связь через общий доступ и комментарии.
  • Проверка: кириллица в шрифтах, контраст по WCAG AA, подписи кнопок и изображений, просмотр на телефоне.
  • Чек-лист перед передачей в разработку; экспорт (PDF, PowerPoint, HTML, .zip) и передача в Claude Code (команды /design и /design-sync; скриншот или PDF для сайта не подходят).
  • Хендоф: короткий отчёт для следующего этапа.
  • В практике (DOCX, сайт музея): токены (цвета, названные по назначению, а не по оттенку), шкала размеров, компоненты и их состояния, правила разработки, WCAG 2.1 AA, prefers-reduced-motion (отключённая анимация), лицензии шрифтов.

Порядок работы (по PDF-конспекту):

  1. ТЗ: начать новый разговор (чтобы в ТЗ не попали посторонние данные) и попросить Claude провести интервью: «Представь, что ты опытный дизайнер. Задай мне по одному вопросы, нужные для ТЗ на страницу записи на новый курс музея. Позже из этой страницы мы сделаем сайт». Готовое ТЗ сверить со структурой занятия 9: цель и главное действие, аудитория, структура, тон, технические требования, открытые вопросы.
    Обратить внимание: в ТЗ нет лишних данных; оно сохранено отдельным файлом; указано, что из результатов выйдет сайт.
  2. Дизайн-система: в разделе «Дизайн» выбрать «Design System», загрузить ТЗ и попросить систему из трёх-пяти цветов, двух шрифтов и базового вида кнопок; сразу попросить проверить контраст и дать системе понятное название (например, «Сайт курса, музей»).
    Обратить внимание: все пары цветов прошли проверку контраста; название понятное. В практике (DOCX) система доводится до состояния «готова к коду»: цвета как токены, шкала размеров, компоненты и состояния, правила (шаг 9 ниже и дополнительная практика).
  3. Макет: создать проект «Design» с этой дизайн-системой и попросить макет главной страницы: hero с названием курса и коротким описанием, заметная кнопка «Записатися», блоки программы, расписания и преподавателей, футер с контактами. Отдельно попросить вариант для телефона. Фото, которых ещё нет, обозначить плейсхолдерами.
    Обратить внимание: два варианта (компьютер и телефон); кнопка главного действия заметна в обоих.
  4. Проверка: проверить шрифты на украинском тестовом тексте, контраст по WCAG AA, подписи кнопок и изображений, затем открыть макет на телефоне. Найденные проблемы исправлять в дизайн-системе, а не в отдельном макете. Попросить Claude провести полную проверку доступности с таблицей проблем.
    Обратить внимание: полная украинская кириллица; исправления внесены в систему.
  5. Обратная связь: все артефакты сначала приватны; поделиться макетом с коллегой или руководителем и попросить оставить комментарии. Самый полезный вопрос: «Что вам хочется сделать на этой странице?» (не объясняя заранее цель страницы). Если ответ совпадает с главным действием из ТЗ, макет работает.
    Обратить внимание: макет увидел кто-то кроме автора; ответ сравнён с ТЗ, правки внесены.
  6. Чек-лист перед передачей в разработку: ТЗ актуально и соответствует макету; дизайн-система сохранена под понятным названием, все пары цветов прошли проверку контраста; есть два варианта макета (компьютер и телефон); у каждой кнопки понятный текст и известно, куда она ведёт; плейсхолдеры обозначены или заменены реальными текстами и фото; шрифты содержат полную украинскую кириллицу и разрешены для использования на сайте; открытые вопросы записаны в ТЗ отдельным пунктом.
    Обратить внимание: недостающие пункты дорабатываются до передачи.
  7. Краткий отчёт (хендоф): попросить Claude составить отчёт: что сделано, как называются ТЗ, дизайн-система и макет, какие вопросы остаются открытыми. Он позволит продолжить работу в новой сессии, не объясняя всё заново (подробнее на первом занятии модуля 4). Сохранить отчёт вместе с ТЗ.
    Обратить внимание: отчёт короткий; ТЗ не потеряно.
  8. Экспорт или передача в Claude Code (два способа для разных целей). Экспорт (PDF, презентация PowerPoint, отдельный HTML-файл или архив .zip, передача в другие сервисы) удобен, когда макет нужно показать руководителю или заказчику либо распечатать. Если цель сайт, дизайн вместе с дизайн-системой передают в Claude Code: команда /design для работы с дизайнами Claude Design и /design-sync для синхронизации дизайн-системы; Claude Code берёт из макета точные цвета, шрифты, отступы и вид элементов (разбор в модуле 4).
    Обратить внимание: скриншот или PDF для создания сайта не подходят: теряются точные значения цветов и шрифтов, состояния кнопок, поведение на разных экранах.
  9. (в практике) Чек-лист «Дизайн-система готова к коду»: токены имеют значения, все пары прошли контраст, акцент только для главной кнопки; шкала проверена на двух языках и устройствах, лицензии разрешают использование; компоненты со всеми состояниями; нет значений, заданных вручную; макет проверен в четырёх вариантах (компьютер и телефон, украинский и английский); правила описаны; хендоф и открытые вопросы сохранены.
    Обратить внимание: этот чек-лист из DOCX строже базового чек-листа из шага 6.

Типичные ошибки, советы:

  • Пропуск этапа: макет без ТЗ или без дизайн-системы почти всегда приходится переделывать.
  • Правки в макете вместо системы: исправления не распространяются на другие страницы и не попадают в код.
  • Макет никто, кроме автора, не видел: автору трудно заметить, что главное действие непонятно. Показать другим и спросить «Что вам хочется сделать на этой странице?»; если ответ совпадает с главным действием из ТЗ, макет работает.
  • Картинка вместо дизайна для сайта: Claude Code приходится угадывать то, что уже было чётко определено.
  • Потерянное ТЗ: в модуле 4 непонятно, на что опираться в спорных решениях.
  • Чем раньше найдена ошибка, тем дешевле исправление: изменить предложение в ТЗ занимает минуту, переделать макет дольше, исправлять запущенный сайт ещё дольше.
  • Экспорт нужен для показа (руководителю, заказчику, печать); для сайта используется передача в Claude Code.
  • В практике (сайт музея): лицензию шрифтов подтверждать на сайте производителя; не оставлять пустых ячеек в таблице токенов; не передавать в Claude Code PDF или скриншоты вместо самой системы и макета.

Итог в одну строку. Пройти полный цикл от ТЗ через дизайн-систему и макет к проверке и обратной связи, подтвердить его чек-листом и передать результат в Claude Code вместе с ТЗ и коротким отчётом, а не картинкой.

Вступление в Claude Code и понятие агента

Модуль 4 · Занятие 1 из 8 · Связь: можно начать с прототипа модуля 3

Обязательно
  • Возможности агента = возможности компьютера
  • Режимы работы: базовый, accept edits, plan, auto
  • Хендоф между сессиями
Желательно
  • Облачная сессия против локальной
  • Уровень «усилий» (high/max/ultrathink)

Цель: Понять, чем агент Claude Code отличается от обычного чата (он не советует, а действует: создаёт файлы, запускает программы), научиться управлять его самостоятельностью через режимы и не терять наработки между сессиями с помощью handoff. Занятие открывает модуль 4, где из дизайна модуля 3 делается настоящий сайт.

Инструменты/понятия:

  • Claude Code (приложение Claude для компьютера, значок </> слева вверху; браузерная версия claude.ai/code); платные планы Pro, Max, Team, Enterprise.
  • Агент (сам планирует шаги, выполняет, корректирует); правило «возможности агента равны возможностям компьютера, на котором он работает».
  • Сессия, контекст («рабочая память» агента), панель «Браузер» (встроенный просмотр страницы), diff (отметка вида «+37 −0»).
  • Режимы: «Ручной режим» (Manual), «Принимать редактирование» (Accept edits), «План» (Plan), «Авто» (Auto); Bypass permissions (на курсе не используется).
  • Handoff (передача работы следующей сессии), файл handoff.md, формат Markdown (.md), CLAUDE.md (постоянные правила проекта).
  • Локальная (Local, «Этот компьютер») и облачная (Cloud) сессии; GitHub для облачной сессии.
  • Уровень усилий (effort): low, medium, high, xhigh, max; команда /effort; слово ultrathink.
  • Cowork (занятие 4) и обычный чат как соседние инструменты.

Порядок работы:

  1. Подготовить отдельную папку проекта (напр. «Сайт_музею»/«Сайт_курсу»), положить туда ТЗ и отчёт занятия 12 (либо один текстовый файл с описанием сайта).
    Обратить внимание: в папке только файлы проекта; агенту доступно всё в выбранной папке, поэтому не открывать «Документы» или весь диск.
  2. Первый запуск: переключиться на Claude Code значком </>, под полем ввода проверить «Этот компьютер», выбрать папку проекта, режим, модель и effort (для старта подходят значения по умолчанию, напр. «Opus 5.5 Средний»). В практике на этом шаге выбирают «Ручной режим». Первый запрос: «Подивись, які файли є в цій папці…».
    Обратить внимание: агент должен реально прочитать файлы (упоминать музей, экскурсии, экспонаты, курсы из ТЗ), а не говорить общими словами. Интерфейс может отличаться от скриншотов, искать значок </> или надпись «Code».
  3. Сравнить обычный чат и Claude Code на одной задаче (страница-заглушка index.html): в чате получаешь код и инструкцию, в Claude Code готовый файл.
    Обратить внимание: считать, сколько действий пришлось бы выполнить вручную.
  4. Режим «План»: агент изучает ТЗ и предлагает план, ничего не меняя; затем в «Ручном режиме» план сохраняется в plan.md («больше ничего не меняй»).
    Обратить внимание: убедиться, что ни один файл не изменился; если в плане есть то, чего нет в ТЗ, это повод уточнить.
  5. «Ручной режим» и «Принимать редактирование»: отклонить предложенную правку (фон страницы светло-серый), затем повторить в режиме «Принимать редактирование» и посмотреть diff.
    Обратить внимание: в ручном режиме отклонённая правка не меняет файл, а Claude спрашивает, как действовать дальше; нельзя нажимать «принять» не читая.
  6. Режим «Авто»: дать многошаговую задачу (добавить описание из ТЗ и проверить, что файл сохранён, а украинский текст отображается без ошибок). Если режима нет в списке, задание пропустить (доступен не для всех аккаунтов и моделей).
    Обратить внимание: сколько шагов агент сделал сам; в «Авто» риски перехватывает отдельная модель-«страж».
  7. Передача дизайна в Claude Code (только в практике): из раздела «Дизайн» экспортировать макет главной через Handoff to Claude Code, готовый англоязычный запрос не отправлять сразу, а переключить режим на «План», дописать просьбу описать блоки, цвета, шрифты, отступы и предложить план; затем в «Принимать редактирование» собрать index.html вместо заглушки; проверить вид на ширине телефона.
    Обратить внимание: порядок блоков и цвета совпадают с макетом и дизайн-системой «Сайт музею» (синий #0433B2, жёлтый #FFE303); украинские буквы в шрифтах отображаются; метки «[ЗАПОВНИТИ]» не заменены выдуманными данными.
  8. Составить handoff в конце работы: цель, что сделано, какие файлы изменены, принятые решения, открытые вопросы, следующий шаг; сохранить в handoff.md.
    Обратить внимание: открыть файл в Блокноте и сверить с реальностью; при пропусках просить дописать.
  9. Продолжить в новой сессии с той же папкой: «Прочитай handoff.md и коротко перескажи…».
    Обратить внимание: понял ли агент состояние работы; чего не хватило в handoff, то дописать.
  10. Дополнительно: сравнить ответ с ultrathink и без него; облачная сессия через claude.ai/code с тренировочным публичным репозиторием GitHub (можно выполнить после занятия 16).
    Обратить внимание: не хранить личных данных в тренировочном репозитории; выставлять максимальный effort «на всякий случай» не стоит (медленнее, быстрее тратится лимит).

Типичные ошибки, советы:

  • Спрашивать совет вместо поручения действия («как мне создать страницу?»); формулировать как задачу («создай страницу…»).
  • Слишком широкая папка проекта.
  • Подтверждать запросы в ручном режиме не читая; если не хочется проверять каждый шаг, осознанно выбрать другой режим.
  • Одна бесконечная сессия: правило «новая задача, новая сессия» (подробнее в занятии 15).
  • Handoff «в голове», без файла.
  • Запоздалое вмешательство: агента можно остановить кнопкой или скорректировать, напечатав уточнение и нажав Enter. В полном diff можно оставить комментарий к строке.
  • Выбор режима: новая или важная работа, «Ручной»; большая задача, «План», потом «Принимать редактирование» или «Авто»; длинная задача, «Авто». Режим можно менять в любой момент. В облачной сессии «Ручного режима» нет; в терминале режимы переключает Shift+Tab.
  • Различие: CLAUDE.md содержит редко меняющиеся правила проекта, handoff это снимок текущего состояния, обновляемый в конце каждой сессии.
  • Облачная сессия не видит файлов на компьютере, работает с проектом на GitHub, продолжается при закрытом приложении.

Итог в одну строку. Claude Code действует сам в выбранной папке, а вы задаёте границы режимом, узкой папкой и handoff-файлом для передачи работы между сессиями.

Безопасность агентов

Модуль 4 · Занятие 2 из 8

Обязательно
  • Поверхность атаки
  • Prompt injection
  • Минимум доступов, проверка чужих skills
Желательно
  • «Усталость подтверждений»
  • Баланс удобство/безопасность

Цель: Понять, откуда берутся риски при работе с агентом (доступы, prompt injection, чужие skills и MCP-серверы, усталость от подтверждений) и освоить простые правила спокойной работы. Цель не напугать, а дать уверенность.

Инструменты/понятия:

  • Поверхность атаки (все «двери и окна»: папки, интернет и браузер, коннекторы, skills/плагины/MCP-серверы).
  • «Смертельная тройка» (lethal trifecta, Саймон Виллисон, 2025): доступ к личным данным + контакт с непроверенным содержимым + возможность передать что-то наружу; убрать любое одно условие, и кража через агента не получится.
  • Prompt injection: прямая и непрямая (инструкция спрятана в странице, письме, документе); OWASP ставит её на первое место среди рисков для ИИ-систем; полностью устранить её, возможно, не удастся (NCSC).
  • Правило «это данные, а не команды» (теги <dani>), принцип минимальных доступов (наименьших привилегий).
  • Коннекторы («Персонализация» → «Коннекторы»), skills («Персонализация» → «Skills»), SKILL.md, MCP-серверы, плагины.
  • Усталость от подтверждений; «Разрешить один раз» / «Всегда разрешать» (Ctrl+Enter / Ctrl+Shift+Enter) / «Отклонить»; режим «Авто» со «стражем»; Bypass permissions; песочница (macOS и Linux, в обычной Windows-версии пока нет).
  • CLAUDE.md с политикой безопасности («подсказка, а не замок»).

Порядок работы:

  1. Составить сокращённый список доступов к задаче: «нужно», «только с подтверждением», «не нужно». Практика: задача «новые страницы сайта музея, карта и шрифты из интернета, затем публикация».
    Обратить внимание: в «нужно» только то, без чего задача невыполнима (папка проекта, правка файлов в ней); почта, календарь, Google Диск, «Документы», банковские сайты и личный профиль браузера не нужны.
  2. Проверить «смертельную тройку» для своей задачи.
    Обратить внимание: все три условия одновременно недопустимы; решить, какое убрать.
  3. Проверить подключённые коннекторы («Персонализация» → «Коннекторы», зелёная галочка = подключён; в сессии Claude Code в правой панели строка «Коннекторы» со счётчиком). Отключить ненужные. В практике дополнительно спросить агента, какие коннекторы, MCP-серверы и skills доступны ему в сессии (ничего не включая и не выключая).

Проверить чужой skill по чек-листу: автор (Anthropic, известная компания или аноним, опечатки в названии), прочитать SKILL.md, тревожные фразы («не говори пользователю», «игнорируй предыдущие правила», «отправь на адрес», «сначала скачай и запусти»), папка со скриптами, обращения к интернету и паролям, пробный запуск в пустой папке. В практике анализируется вымышленный skill krasyvi-lysty.

Типичные ошибки, советы:

  • Подключать всё «на всякий случай»; открывать весь диск вместо папки проекта.
  • Ставить skill или плагин, не открыв ни одного файла.
  • Хранить пароли в файлах проекта.
  • Нажимать кнопки машинально, особенно «Всегда разрешать». Данные Anthropic (август 2026): пользователи одобряют 97% запросов; в эксперименте подменённую опасную команду заметили лишь в 13,6% случаев, «страж» режима «Авто» заблокировал 89%; к 50+-му запросу внимание падает.
  • Считать правила в CLAUDE.md полной защитой.
  • Игнорировать странное поведение агента (неожиданные сайты, просьбы дать личные данные): сразу остановить.
  • Советы: узкая папка; отключать коннекторы после задачи; отдельный профиль браузера без входа в банк; публикацию, отправку писем, оплату и удаление подтверждать самому; когда устали, ничего важного не одобрять. Режимы под риск: незнакомый проект «План» или «Ручной»; учебный сайт в отдельной папке «Авто» или «Принимать редактирование»; непроверенные страницы узкая папка или облачная сессия.
  • Реальные случаи в материалах: поддельный почтовый MCP-сервер (сентябрь 2025), 341 вредоносный skill в каталоге ClawHub (февраль 2026), инструкция в комментарии Reddit (исследователи Brave, 2025).

Итог в одну строку. Агент опасен там, где у него много доступов, поэтому давайте минимум доступов, считайте чужой текст данными, проверяйте чужие расширения и читайте каждое подтверждение.

Промпты для агентов и экономия контекста

Модуль 4 · Занятие 3 из 8

Обязательно
  • Персона + знания
  • Позитивные формулировки вместо запретов
  • Что такое контекст и почему длинные чаты ухудшаются
Желательно
  • Кросс-модельная проверка
  • Хендоф, правило «одна задача — одна сессия»

Цель: Научиться писать промпты, которые агент выполняет точно (с критериями готовности), и беречь «рабочую память» агента: не допускать порчи контекста длинными и «замусоренными» сессиями.

Инструменты/понятия:

  • Формула промпта для агента: персона + знание + задание + критерии готовности (развитие пятиэлементной модели занятия 1).
  • Позитивные формулировки вместо запретов; объяснение причины («зачем»).
  • Контекст, токены, context rot («гниение контекста», Anthropic; исследование Chroma 2025 на 18 моделях), строка «Контекст» в правой панели сессии, /context, /compact, автоматическое сжатие, кнопка «Новый» (в практике «Создать»).
  • Принцип «одна задача, одна сессия»; handoff (занятие 13).
  • Кросс-модельная проверка (Gemini, ChatGPT или Claude в новой сессии с другой моделью).

Порядок работы:

  1. Переписать слабый промпт («Ти найкращий веб-дизайнер у світі. Зроби класну сторінку… Не помились.») по формуле, указав файлы для чтения (ТЗ, plan.md, index.html, styles.css).
    Обратить внимание: роль не добавляет знаний (исследование Мичиганского университета: 162 роли, 2410 вопросов, точность не растёт); в промпте нужен хотя бы один факт о проекте; каждый критерий проверяется ответом «да» или «нет». В практике можно попросить Claude задавать вопросы по каждой части формулы и проверить готовый промпт.
  2. Переписать запреты в проверяемые требования («не помиляйся» → «после создания открой страницу и проверь ссылки, текст, телефон»; «не придумывай факты» → «используй только данные из ТЗ, чего не хватает, запиши в открытые вопросы»; «основной текст не менее 18 пикселей»). Для двух добавить объяснение «зачем».
    Обратить внимание: чёткие запреты безопасности (из занятия 14) нормальны, плохо работают расплывчатые запреты о качестве.
  3. Сравнить результаты слабого и сильного промпта в двух новых сессиях (в практике слабая страница сначала переименовывается в courses-slabkyi.html, затем сравнивается по таблице с ТЗ и удаляется).
    Обратить внимание: на слабой странице вероятны выдуманные курсы, цены, расписание; на сильной только три курса из ТЗ и отчёт по каждому критерию.
  4. Посмотреть на контекст: значение в строке «Контекст» (или /context) до и после просьбы прочитать все файлы проекта.
    Обратить внимание: так выглядит «заваленный стол»; обсудить, какой файл занял больше всего места и нужны ли были все.
  5. Ошибка в начале: начать сессию с заведомо неверного факта, затем исправить и попросить ещё тексты; сравнить с сессией, начатой сразу с правильным фактом. В практике: график музея «каждый день 9:00–21:00» вместо «вторник–суббота, 10:00–18:00».
    Обратить внимание: в новых текстах не должны «проскакивать» неверные «каждый день» и «до 21:00»; обратить внимание на «анонс выходного дня» (в воскресенье музей закрыт); на коротких сессиях эффект слабее.
  6. Кросс-модельная проверка: другой модели дать только результат и критерии (без истории создания), просить сообщать лишь о нарушениях критериев; в Claude Code передать только обоснованные замечания.
    Обратить внимание: проверяющий почти всегда что-то найдёт; стилистические пожелания отбрасывать, итоговое решение за человеком.
  7. Handoff и новая сессия: обновить handoff.md, начать новую сессию кнопкой «Новый»/«Создать» (проверить выбранную папку), сравнить объём контекста.
    Обратить внимание: новая сессия правильно называет следующий шаг, контекста занято намного меньше.
  8. Практика дополнительно: страница экспонатов exhibits.html по формуле (с отметкой «[ЗАПОВНИТИ]» для недостающих данных, alt-текст, мобильная вёрстка, ссылка в меню на всех страницах); сравнение требования с причиной и без (alt-текст для людей со скринридерами); «свежий взгляд», проверка сайта в новой сессии в режиме «План»; /compact.

Типичные ошибки, советы:

  • Роль вместо знаний («ты лучший эксперт» без фактов).
  • Расплывчатые запреты («не ошибайся», «не выдумывай») вместо проверяемых критериев.
  • Нет критериев готовности: агент останавливается, когда ему «кажется», что готово.
  • Сессия-«свалка» из разных задач; бесконечные исправления вместо новой сессии с лучшим промптом (совет: если дважды исправляли одно и то же, начать заново).
  • Проверка своим же автором в той же сессии.
  • Исправлять всё, что нашёл проверяющий.
  • Совет: объяснять причину требования, модель сама распространит правило на похожие случаи. Правило «одна задача, одна сессия» не абсолютное: если вся история важна для одной сложной задачи, можно продолжать.

Итог в одну строку. Давайте агенту факты, файлы и проверяемые критерии вместо ролей и запретов и начинайте новую сессию с handoff, пока контекст не «зарос».

Git, терминал и GitHub: основы

Модуль 4 · Занятие 4 из 8

Обязательно
  • Зачем git
  • Базовые команды: cd, ls, git status, коммит
  • Ветки (branch)
Желательно
  • Dev-сервер (npm run dev)
  • GitHub и pull request

Цель: Освоить три базовых инструмента разработчика: терминал (команды текстом), git (история изменений проекта с возможностью вернуться назад) и GitHub (онлайн-хранилище и совместная работа). Команд немного, и Claude Code выполнит любую из них за вас и объяснит результат.

Инструменты/понятия:

  • Терминал (PowerShell в Windows, строка-приглашение «PS C:\...>»); открытие: «Термінал» в заголовке сессии или Ctrl+`.
  • Команды: pwd, ls, cd, cd .., cls/clear; клавиши Tab, стрелка вверх, Ctrl+C.
  • Git: репозиторий, коммит, рабочая копия, индекс (staging area), .git, .gitignore; команды git --version, git config, git init, git status, git add ., git commit -m, git log --oneline, git diff, git restore ..
  • Ветки: git branch, git switch -c, git switch, git merge, git branch -d; конфликт слияния.
  • Dev-сервер (localhost, порт), панель «Браузер» (значок глобуса, Ctrl+Shift+B), .claude/launch.json, npm run dev (для простых HTML-файлов не обязателен).
  • GitHub: git remote add origin, git push, git pull, git clone, Pull request (PR), Public/Private; GitHub CLI (gh); Git for Windows (Git Bash, Git Credential Manager).

Порядок работы:

  1. Первые шаги в терминале: открыть в сессии Claude Code, pwd, ls, подняться cd .. и вернуться через Tab.
    Обратить внимание: сверить ls с Проводником; если ls выдаёт ошибку, вы в CMD (там dir); cd .. именно с двумя точками. Не вставлять в терминал команды из непроверенных источников.
  2. Установить и настроить git: git --version; при отсутствии установить Git for Windows с git-scm.com (все варианты по умолчанию, перезапустить приложение Claude); выполнить четыре git config --global (user.name, user.email, init.defaultBranch main, core.quotepath false); проверить git config --global --list.
    Обратить внимание: имя и почта видны всем, если репозиторий публичный (можно скрыть почту в GitHub: Settings → Emails → «Keep my email addresses private»); core.quotepath false нужна для украинских названий файлов.
  3. Первый коммит: git status (скорее всего «not a git repository»), git init, git add ., git commit -m "…", git log --oneline.
    Обратить внимание: после git add имена файлов зелёные; итог, «working tree clean»; хорошее описание коммита конкретное, а не «правки».
  4. Коммит руками агента: агент вносит правку (напр. строка © в подвал), вы смотрите git status и git diff (выход Q), просите предложить описание и сделать коммит.
    Обратить внимание: в git diff изменения только в нужном месте; описание коммита понятное.
  5. Вернуться к сохранённой версии: намеренно неудачная правка (заменить заголовки на «ТЕСТ»), затем откат через агента (с показом, что будет потеряно) или git restore ..
    Обратить внимание: git restore необратимо отменяет несохранённые изменения, поэтому перед большой задачей для агента нужен коммит.
  6. Ветка и слияние: git switch -c, правка (кнопка «Нагору»/«Записатися на курс») и коммит, переключение туда-обратно, git merge, удаление слитой ветки.
    Обратить внимание: названия веток латиницей через дефис; перед переключением сохранить изменения коммитом; при конфликте просить Claude показать обе версии, решение принимать самому.
  7. Dev-сервер в панели «Браузер»: попросить агента запустить, назвать команду и адрес; изменить цвет кнопки (#0433B2), остановить сервер («Зупини dev-сервер» или Ctrl+C), закоммитить.
    Обратить внимание: в примере агент использовал встроенный сервер Python с --bind 127.0.0.1 (виден только на этом компьютере, сам не обновляет страницу); 404 на favicon.ico не проблема; при нехватке программы агент предложит установить, ставить только с официальных сайтов.
  8. Сайт на GitHub: создать пустой репозиторий на github.com/new (без README), проверить папку на секреты и создать .gitignore, подключить origin, git push, войти в GitHub при первом push.
    Обратить внимание: в репозиторий не должны попасть пароли и личные данные; пароль, попавший в коммит, остаётся в истории даже после удаления файла; при сомнениях начинать с приватного репозитория.
  9. Дополнительно, Pull request: ветка, коммит, git push -u origin ветка, «Compare & pull request» → «Create pull request», вкладка «Files changed» (комментарий к строке), «Merge pull request» → «Confirm merge», затем git switch main и git pull.
    Обратить внимание: PR это открытое слияние с обзором и комментариями (аналогия, документ на согласование); статус меняется с Open на Merged.
  10. Дополнительно, облачная сессия со своим репозиторием: claude.ai/code → выбор репозитория → «Установить додаток Claude для GitHub» → Only select repositories (не All repositories) → правка handoff.md → перенос через PR → git pull на компьютере.
    Обратить внимание: приватный репозиторий облачная сессия видит только после установки приложения; доступ только к нужному репозиторию (принцип минимальных доступов).

Типичные ошибки, советы:

  • Работа без коммитов: откатываться не к чему.
  • Описания «правки», «ещё правки», «финал2».
  • Эксперименты прямо в main вместо отдельной ветки.
  • Пароли в репозитории (удаление файла не убирает их из истории).
  • Путать git и GitHub: коммит только на компьютере, пока не выполнен git push.
  • Удалять папку .git (исчезает вся история).
  • Запускать непонятные команды.
  • Названия веток: латиница, без пробелов. В старых инструкциях вместо git switch встречается git checkout.
  • В материалах основная ветка названа main (настройка init.defaultBranch main); в разных версиях git она может называться master. Практика предполагает main.

Итог в одну строку. Git с коммитом перед каждой большой задачей агента делает любой эксперимент обратимым, а GitHub хранит копию проекта и ведёт к публикации.

  • Генераторы статических сайтов (Jekyll, Hugo, Astro) упомянуты; на курсе страницы из .md создаёт агент.
  • Cowork для текстов без кода (/schedule, раздел Scheduled).
  • Ветка, PR (занятие 16).

Порядок работы:

  1. Провести первое исследование: «+» → «Дослідження» (автоматически включается «Пошук в інтернеті»). Запрос включает тему и границы, цель, аудиторию, требования к источникам, формат отчёта. Отчёт сохранить как research-report.md и положить в папку сайта.
    Обратить внимание: чем точнее запрос, тем меньше лишнего; для простых вопросов Deep Research не нужен (быстрее и дешевле в лимите). Если режим не запустился, попросить прямо.

    Обратить внимание: отчёт это не истина, а организованный черновик (пример: GPTZero нашёл 100 выдуманных ссылок в 51 статье NeurIPS 2025); первоисточники надёжнее блогов.
  3. Составить контент-план из 5 статей (название, ключевая мысль, аудитория, источники из отчёта, объём 600–900 слов, порядок) в том же чате, где отчёт; сохранить как content-plan.md; сделать коммит (в практике в ветке statti).
    Обратить внимание: статьи идут от простого к сложному и не повторяются; для каждой есть источники в отчёте, иначе заменить тему или провести более узкое исследование. В практике просят при возможности связать статью с экспонатом музея.
  4. Разметить текст в Markdown (заголовки #, ##, абзацы, жирный, курсив, списки, ссылки, изображения с описанием, цитаты) на тестовом articles/test.md; попросить агента проверить разметку.
    Обратить внимание: после # обязателен пробел; сохранять в UTF-8; git diff для .md показывает изменённое слово, а для .docx только «файл изменён».
  5. Написать статью № 1 агентом (файл на латинице с номером, напр. 01-mesm.md, 600–900 слов, без фактов не из отчёта, с разделом «Джерела»), внести свои правки в .md, затем превратить статьи в HTML-страницы и создать articles.html со списком и пунктом «Статті» в меню; посмотреть в панели «Браузер» и на ширине телефона; удалить test.md, сделать коммит.
    Обратить внимание: файл .md это «оригинал»: правки только в нём, затем просить агента обновить страницу (иначе появятся две версии статьи); пункт «Статті» на всех страницах, оформление как у остального сайта.
  6. Кросс-модельная проверка фактов (Gemini или ChatGPT): для каждого утверждения статус «подтверждено/сомнительно/неверно» и ссылка; отдельно отметить формулировки, которые стоит смягчить. Исправления вносятся в .md, страница обновляется, коммит.
    Обратить внимание: проверяющий тоже ошибается, проверять его ссылки; пример со словом «первый»: МЭСМ точнее называть «первой в СССР универсальной программируемой электронной ЭВМ; некоторые авторы называют её первой в континентальной Европе».
  7. Практика дополнительно: PR с разделом «Статті» (git push -u origin statti, PR, «Files changed», слияние, git pull); связь статьи с экспонатом (ссылки «Читати статтю» и «Подивитися експонат» в ветке stattia-eksponat); сравнение с Gemini/ChatGPT deep research.
    Обратить внимание: изменения попадают в main через PR, а не напрямую.

Типичные ошибки, советы:

  • Расплывчатый запрос на исследование.
  • Отчёт как готовая статья (его надо сократить, адаптировать, проверить).
  • Ссылки без проверки.
  • Контент-план без источников (агент «допишет» из своих знаний).
  • Текст в Word вместо Markdown (скрытое форматирование, MsoNormal, mso-…, ломает вид и git не показывает изменения); Markdown даёт чистый HTML, текст отделён от дизайна.
  • Правки в HTML вместо .md.
  • Громкие слова без доказательств («первый», «единственный», «уникальный»).
  • Сайт на этом занятии «публикуется» только локально и на GitHub; публикация в интернете в занятии 18. Cowork подходит для документов (Word, PDF, таблицы), Claude Code если текст должен стать страницей сайта и пройти PR; Cowork тоже может ошибаться в фактах.
  • Режим «Дослідження» тратит лимит быстрее обычных вопросов; интерфейсы Gemini/ChatGPT часто меняются.

Итог в одну строку. Исследование даёт черновик, а не истину: пишите статьи в Markdown по плану с источниками, проверяйте факты другой моделью и решайте спорное сами.

Хостинг, домен и деплой

Модуль 4 · Занятие 6 из 8

Обязательно
  • Домен, DNS, субдомен
  • Деплой на сервер
  • Отдельный сервис для рассылок
Желательно
  • SSH-ключ вместо пароля
  • Автоматическая публикация (CI/CD)

Цель: Открыть сайт для всех: понять, как сайт получает адрес в интернете (домен, DNS, поддомен), опубликовать его на GitHub Pages с автоматической публикацией после каждого слияния, а также узнать о SSH-ключах и об отдельных сервисах рассылок.

Инструменты/понятия:

  • Хостинг, домен, регистратор, DNS, IP-адрес; записи DNS: A, AAAA, CNAME, MX, TXT, NS; поддомен (напр. kurs.example.org); nslookup, Resolve-DnsName, WHOIS.
  • Деплой, статический сайт; GitHub Pages (Deploy from a branch; Source: GitHub Actions), .nojekyll, Unpublish site.
  • CI/CD, GitHub Actions, вкладка Actions, workflow в .github/workflows/*.yml.
  • Custom domain, Enforce HTTPS, подтверждение домена TXT-записью.
  • SSH (Secure Shell), приватный и публичный ключ, ssh-keygen -t ed25519, passphrase, ssh -T git@github.com, секреты репозитория (Settings → Secrets and variables → Actions); VPS.
  • Рассылки: SMTP, SPF, DKIM, DMARC, double opt-in; сервисы Brevo, MailerLite, Mailchimp.

Порядок работы:

  1. Понять путь запроса: браузер спрашивает DNS, DNS отвечает IP-адресом, браузер получает файлы с сервера и показывает страницу. Проверить nslookup github.com, -type=MX gmail.com, -type=NS example.org, -type=TXT gmail.com; попросить агента объяснить результат. Практика: также nslookup [логин].github.io.
    Обратить внимание: «Non-authoritative answer» нормально (ответ из кэша); v=spf1 это SPF; nslookup только читает, его безопасно разрешать; адрес [логин].github.io отвечает ещё до публикации (запись-шаблон в зоне github.io), а будет ли сайт, решает GitHub (до публикации откроется 404). Менять записи DNS должен человек, пароль от панели реестратора агенту не давать.
  2. Подготовить сайт к публикации в отдельной ветке (pidgotovka-do-publikatsii): главная index.html в корне, все пути относительные без начальной косой черты, найти битые ссылки, добавить пустой .nojekyll; показать список правок перед коммитом; слить через PR.
    Обратить внимание: сайт на GitHub Pages живёт в «подпапке» /название-репозитория/, поэтому /images/foto.jpg не найдётся; images/foto.jpg работает.
  3. Проверить репозиторий на секреты и его видимость: пароли, ключи, токены, личные данные, внутренние документы (в практике, включая Word-файлы), не только в файлах, но и в истории коммитов. В практике студент даёт агенту одноразовое разрешение, поскольку в CLAUDE.md есть правило не искать пароли; найденные секреты агент не выводит полностью, только файл, коммит и первые символы.
    Обратить внимание: на бесплатном тарифе GitHub Pages работает только для Public-репозиториев. Если в истории есть пароль или внутренние документы, репозиторий публичным не делать (в практике: обратиться к преподавателю, проще создать новый чистый репозиторий с текущими файлами); пароль заменить в сервисе. Решение о видимости принимает человек.
  4. Включить публикацию вручную (Settings → Pages → Deploy from a branch → ветка main, / (root) → Save), дождаться «Your site is live at …», проверить изображения, стили, меню, страницы и вид на телефоне.
    Обратить внимание: настройки публикации лучше менять самому, а не поручать агенту; обновления могут появляться до 10 минут. Лимиты: сайт до 1 ГБ, трафик около 100 ГБ в месяц; нельзя использовать для интернет-магазинов и передачи паролей/карт, форму с личными данными делать отдельным сервисом (напр. Google Формы).
  5. Автоматическая публикация (CI/CD): ветка → правка → dev-сервер → PR → слияние в main → GitHub Actions публикует сайт. Следить за значком во вкладке Actions (зелёная галочка, красный крестик, жёлтый кружок); обновить сайт Ctrl+F5; записать адрес и порядок публикации в handoff.
    Обратить внимание: теперь main это то, что за несколько минут увидят все, поэтому правки только в отдельной ветке и через PR; при ошибке публикации сайт не ломается, виден предыдущий вариант.
  6. Автоматическая проверка ссылок (практика): два workflow GitHub Actions: проверка на каждый PR в main и публикация на push в main с той же проверкой; Settings → Pages → Source: GitHub Actions; затем намеренно сломать ссылку в тестовой ветке и убедиться, что проверка в PR становится красной; PR с пометкой [ТЕСТ] закрыть без слияния, ветку удалить git branch -D.
    Обратить внимание: права минимальные, данные внешним сервисам не отправляются; просить агента объяснить каждую строку workflow (это код, который GitHub выполняет автоматически, как и в случае с чужим skill из занятия 14).
  7. Подготовить план поддомена (для администратора домена): подтверждение домена TXT-записью; сначала домен вносится в GitHub (Custom domain), потом в DNS создаётся CNAME kurs → логин.github.io (без названия репозитория); проверка nslookup -type=CNAME; Enforce HTTPS; сохранить план в deploy-plan.md.
    Обратить внимание: не создавать записей-шаблонов *.example.org; изменения DNS идут до 24 часов; у агента нет и не будет доступа к DNS-панели. Для корня домена вместо CNAME нужны четыре записи A (185.199.108.153–185.199.111.153), но поддомен проще и безопаснее.
  8. Практика, дополнительно: SSH-ключ для GitHub (ssh-keygen, добавить .pub в Settings → SSH and GPG keys, ssh -T git@github.com, правило про .ssh в политику безопасности); форма подписки на рассылку (сервис, подтверждение домена, встраивание HTML-кода формы в футер в отдельной ветке; пояснение для подписчиков, политика конфиденциальности, double opt-in).
    Обратить внимание: приватный ключ никому не отправлять и не вставлять в чат, агенту не нужно его читать; адрес e-mail это личные данные; не сливать ветку, пока рядом с формой нет пояснения. Рассылку не отправлять из личной почты или собственного сервера: письма уходят в спам, ящик могут заблокировать (требования Gmail с февраля 2024).
  9. Практика, дополнительно: план «полноценного сайта» (full-site-plan.md): что понадобится, если посетители будут отправлять данные через форму (хостинг, база данных, домен, стоимость, риски для личных данных); короткий адрес [логин].github.io через переименование репозитория и git remote set-url origin ….
    Обратить внимание: агент ничего не покупает и не регистрирует; цены приблизительные, их надо проверять на сайтах сервисов.

Типичные ошибки, советы:

  • Приватный репозиторий на бесплатном тарифе (Pages не включается); менять на Public только после проверки на секреты, включая историю.
  • Абсолютные пути: пропадают изображения и стили.
  • Правки прямо в main при включённой автопубликации.
  • Сначала DNS, потом GitHub: чужой человек может занять поддомен; то же с записями *.
  • Ждать мгновенного результата от DNS (до 24 часов).
  • Передать агенту пароль или приватный ключ.
  • Рассылка из личной почты или со своего сервера.
  • Забыть продлить домен (включить автопродление или напоминание).
  • Пример example.org зарезервирован для документации; подставляйте свой домен.

Итог в одну строку. Сайт публикуется цепочкой «файлы, репозиторий, GitHub Pages, домен», а после включения автопубликации каждая правка в main через несколько минут видна всем, поэтому всё идёт через ветку, проверку и PR.

Субагенты и Skills в Claude Code

Модуль 4 · Занятие 7 из 8

Обязательно
  • Субагент = skill с конфигурацией
  • Статусы draft/approved
  • «Сначала человек вручную, потом более дешёвый стажёр»
Желательно
  • Выбор модели и усилий под задачу
  • Ревью конфигурации перед утверждением

Цель: Научиться передавать повторяющуюся проверку по списку субагенту (отдельному помощнику со своим контекстом, ограниченными правами и моделью) и разобраться, как устроены skills в Claude Code и чем они отличаются от субагентов. Сквозной пример: субагент article-checker, проверяющий статью перед коммитом.

Инструменты/понятия:

  • Субагент: файл .claude/agents/название.md; поля name, description («используй проактивно» / use proactively), tools, model (haiku, sonnet, opus, fable, inherit или точное имя), effort (необязательное), skills.
  • Skill: папка .claude/skills/название/SKILL.md (поля name, description), вызов вручную /название, /reload-skills; личные skills в домашней папке .claude/skills.
  • Встроенные субагенты: Explore, Plan, General-purpose; строка «Агента запущено», панель субагента.
  • Инструменты: Read, Grep, Glob (чтение), Edit, Write (изменение), Bash (команды), WebFetch, WebSearch.
  • Draft/approved: папка agents-drafts (чернетка) и .claude/agents (утверждено); checklist-article.md; правило в CLAUDE.md.
  • Принцип «руководитель, практикант»; рецензия конфигурации; кросс-модельная проверка.

Порядок работы:

  1. Выбрать задачу для автоматизации: выписать 3–5 повторяющихся задач, отметить: можно ли описать списком критериев, есть ли чёткий результат, нужно ли менять файлы. Выбрать одну (на примере проверка статьи перед коммитом); в практике можно сверить выбор с Claude в обычном чате.
    Обратить внимание: субагент окупается на рутине; для одноразовой задачи хватит обычного запроса.
  2. Проверить вручную: самостоятельно проверить статью № 1 (заголовки, описания изображений, наличие файлов изображений, раздел «Джерела», громкие слова «первый»/«единственный»), в практике также попросить агента сделать то же и перечислить критерии, затем объединить в checklist-article.md.
    Обратить внимание: каждый критерий проверяется ответом «да» или «нет»; нельзя написать хорошую инструкцию для задачи, которую сам ни разу не выполнял. Цепочка из четырёх шагов: вручную, чеклист, практикант (субагент на дешёвой модели), выборочная проверка.
  3. Создать skill article-format в ветке subagent-article-checker (в «Ручном режиме»): .claude/skills/article-format/SKILL.md с правилами оформления статей; проверить, что он появляется по /art с пометкой (project) и срабатывает сам в новой сессии (запрос «Склади план статті № 2 з контент-плану»).
    Обратить внимание: если .claude/skills создана посреди сессии, ввести /reload-skills или начать новую сессию; skills от других людей сначала просматривать (занятие 14).
  4. Создать черновик субагента agents-drafts/article-checker.md: tools только Read, Grep, Glob; model haiku; skills: article-format; не исправляет; отчёт из трёх разделов (критичное, стоит исправить, проверить человеку) с номером строки и цитатой, при отсутствии замечаний «Готово до коміту». Попросить агента написать файл самому по описанию; закоммитить черновик.
    Обратить внимание: папка agents-drafts Claude Code не применяет; agents-drafts не .claude/agents, иначе субагент начнёт работать до рецензии; пустое поле tools даёт все инструменты основной сессии; субагент не видит вашего разговора и не может переспросить, инструкция должна быть самодостаточной; статус определяется папкой, а не строкой status: draft в файле.
  5. Рецензия конфигурации по списку (название и описание, инструменты, модель и усилия, инструкция с позитивными проверяемыми критериями и форматом отчёта, тест, происхождение) и кросс-модельная проверка черновика в Gemini/ChatGPT; внести обоснованные исправления, не меняя tools и модель.
    Обратить внимание: каждое исправление выбираете вы сами; файл публичного репозитория читает каждый, секреты в инструкции не записывать.
  6. Тест и утверждение: создать articles/test-errors.md с намеренными ошибками (изображение без описания, ссылка на несуществующий файл изображения, пропущенный уровень заголовка, слово «первый», нет «Джерела»), перенести субагента в .claude/agents, вызвать «Використай субагента article-checker, щоб перевірити …», открыть панель по строке «Агента запущено» (модель haiku, только чтение), проверить и на правильной статье № 1. Если результат устраивает, удалить тестовую статью, коммит «Затверджено субагента article-checker», PR в main; иначе вернуть файл в agents-drafts, доработать и повторить.

  • Реальные данные в облачном агенте (например, список участников с телефонами): для обучения только синтетика.
